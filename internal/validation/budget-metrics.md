# Opt-in budget metrics and periodic collection

Expose three observable integer gauges for each budget's active operations, configured total capacity and admission-closed flag. Tenant budgets expose active tenant count and per-tenant capacity as two additional gauges. CreateMetrics returns an owned Meter with fixed aggregate instrument names and no tags. Creating instruments performs no dispatch or tenant authority work. The host disposes its meter and controls observation scheduling. Gauges are sampled separately and can describe different moments under concurrent mutation.

Verify actual MeterListener collection while an owned operation waits in cleanup, after closing admission and after drain. All expected names and values must be present, tags empty and factory counts unaffected by observation. Disposing the meter stops its observations. Listener callback failures must remain on the explicit collection path and cannot prevent a subsequent operation.

Measure collection on one thread at four controlled stages using the exact committed Release binary and pinned SDK. Reuse the real Core and protected tenant held-cleanup fixture. Create both owned meters and one listener outside measurement. For each stage take 20 collections separated by Thread.Sleep(10) outside the measured region. Record actual start timestamps, elapsed ticks and current-thread allocation for each RecordObservableInstruments call including eight fixed-value validation callbacks. Retain the first collection and all subsequent collections without warmup filtering. Validate every callback value against the stable stage and terminal handler ownership. Meter creation, delay, JSON serialization and output writes are excluded. One complete Windows run then one WSL run follows all builds and correctness checks. Report ranges and medians of raw collections, actual cadence and measured allocation without a performance pass threshold. Existing canonical benchmark gates remain as recorded.

The final source also allows a host-selected meter name. One preliminary source preparation validated the default-only API, then the final revision repeated the required checks with custom naming. No timing observations were run on the preliminary revision. The periodic collection protocol itself stays as declared above.
