# ADR0011: Prove collector connection readiness and retain failed-phase telemetry

2026-10-28. Accepted for the user-authorized continuation of #9/#11. Engine remains `6804271d429106864e01e4ec546a41dff771f84b`; #3 remains Blocked. This supplements ADR0009/0010 without changing the original workload or budgets.

Canonical03 retained an HTTP Engine 2000/s diagnostic preflight failure: 37 offered drops among 4000 requests, with four observed TLS connections before the phase versus 128 for its baseline. Equal preparation request counts did not establish equal physical readiness. Missing failed-phase connection events and aggregate-only GC observations prevent attribution to TLS, GC, JIT or an Engine capacity ceiling. Preserve that attempt unchanged.

## Decision frozen before new measurements

Prepare the same two read-only get/list operations and 128 read-only get operations for both variants. For the latter, request exact HTTP/1.1 with `ResponseHeadersRead`, retain all 128 nonempty response bodies unread simultaneously, then release a common barrier and consume/validate every body. All 128 headers and body reads share one 30-second preparation deadline. On failure, release/cancel and join all children before retaining failure evidence. Do not increase the 128 request cap, retry preparation or weaken TLS/certificate checks. Retain per-request header/body/barrier timestamps, observed TLS events and the attained held-response count. Verify the actual barrier, rather than assuming Task.WhenAll proves socket parity.

The load pool is fresh and separate from the identically configured control pool used for reset/get/list/state/metrics. Require 128 distinct load-pool TLS connection identities and 128 held HTTP/1.1 responses at the barrier; retain control connections separately rather than mistaking cumulative historical handshakes for 128 current load connections. The initial get/list still warm shared code paths. This explicitly changes collector pool topology for both variants; it is not an isolated Engine change. Where chunked responses omit Content-Length, reject explicit zero length at headers and require actual positive body bytes and full validation after release before entering preflight.

Microsoft documents that [ResponseHeadersRead completes before reading response content](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpcompletionoption); the content read requires its own cancellation deadline. The physical-readiness claim is limited to the observed HTTP/1.1 held-response barrier. It does not guarantee that sockets remain healthy indefinitely or establish production capacity.

Persist TLS snapshots and client phase boundaries for every entered phase, including a failed collector preflight. Keep connection handshake timestamps on the same Stopwatch clock as request rows. Boundary GC/pool counters remain aggregate observations, not temporally localized causes. Managed failures must retain all observed request rows and a structured failure report; abrupt process loss can still invalidate in-memory evidence.

Connection preparation is outside the fixed offered schedule and is identically applied to both variants. It does not move server startup, key loading, full readiness hashing or the first verified request outside the existing startup clock. No new packages, SDK/runtime version, compilation mode, thread-pool minimum, latency floor or scheduling change is selected.
