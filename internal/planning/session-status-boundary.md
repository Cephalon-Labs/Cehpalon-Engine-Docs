## Consumer configuration

The application supplies a trusted IIdentitySessionStatusSource and explicitly decorates its authenticated source in selected composition:

```csharp
IIdentitySource authenticated = new AspNetCoreJwtIdentitySource(
    accessor, "Bearer", timeProvider: null, sessionClaimType: "sid");
IIdentitySource protectedIdentity = new SessionValidatingIdentitySource(
    authenticated, trustedSessionStatus, TimeSpan.FromSeconds(30));
// Pass protectedIdentity as TenantSecurityServices.IdentitySource.
```

JWT/JWE signature/decryption/issuer/audience validation remains with the configured established handler. The new fourth constructor argument selects a unique bounded claim from that successful ticket. The original three-argument JWT constructor and four-argument IdentitySnapshot signature remain available. A SessionBoundTicketIdentityMapper wraps a cookie/custom ticket mapper using the same successful configured ticket; it rejects a conflicting existing inner session binding. Constructing DTOs, setting a User flag or submitting a tenant/session header establishes no authority.

Status responses bind exact issuer/subject/authentication scheme/session ID, active state and validity. Each protected ResolveAsync calls the trusted source afresh, including after a host ticket has been cached. No cache or stale fallback is installed. Anonymous/sessionless identity skips provider I/O and denies in this selected mode. Missing/inactive/misbound/future/expired status denies; cancellation and provider faults preserve the existing cancellation/fault path and required operation audit. Session IDs/tokens/keys/claim bags never enter framework audit/history envelopes.

The application explicitly chooses a positive observation lifetime up to five minutes. Both upstream authentication and session lookup consume its UTC/monotonic budget, including when UTC stalls. Completion checks clocks/validity and intersects identity/status expiry with the initial UTC cap and remaining monotonic budget. Returned identity preserves SessionId and uses completion UTC as a lower bound. The cap is checked at completion and does not terminate an uncooperative provider. Hosts/sources own I/O deadlines and cancellation; the portable decorator observes its supplied token, including linked request cancellation where configured. No background lookup or automatic renewal runs. Disabled composition does not construct a session provider or invoke its factory/lookup; fixture controls are counted separately from actual provider construction.

## Session and tenant boundaries

A session ID is unique per login/generation, partitioned with principal and scheme. Providers must retain revocation/tombstones and never reuse/reactivate an ID while old credentials might exist. A response-only version cannot provide anti-replay binding; this scope omits that misleading guarantee. A separate session of the same user can remain active; a new login uses a new ID. Host/provider policy may invalidate all a user's sessions, but the engine does not provision a session database or implement OAuth logout/introspection/revocation endpoints.

Fresh tenant membership/resource/RBAC/ABAC still follows the session check. Switching A/B remains request-local authorization; a valid session grants no cross-tenant bypass. Read sets pin the same principal/scheme/session ID across initial and child resolutions and preserve it when clamping identity validity. Midaggregate session change/revocation denies the complete response; earlier authorized reads may have run and keep their audit records. Required audit records authorization/denial/fault/cancellation using existing verified tenant-history semantics, without raw session IDs. Durable session-management audit is a separate host/provider responsibility.

This is an observation boundary, not continuously subscribed revocation or an atomic transaction with later membership/policy/audit waits, business admission, provider writes or response delivery. Already admitted work may finish. The observation's monotonic origin is not carried through later awaits; when UTC stalls after returning, maximumObservationLifetime is not an end-to-end admission deadline. Host AuthenticateAsync/HttpContext.User/cached cookies may still report authentication. Ordinary RequireAuthorization routes and plain Core/codegen need explicit equivalent wiring; the decorator does not globally clear tickets or sign out. Protected engine denial uses access.denied/HTTP403 rather than a new global401/logout protocol. Provider latency and per-resolution work remain unbenchmarked.

Primary references: [ASP.NET backend change checks](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/cookie#react-to-back-end-changes), [OAuth introspection](https://www.rfc-editor.org/rfc/rfc7662.html), [OAuth revocation](https://www.rfc-editor.org/rfc/rfc7009.html). This local port does not claim those protocol implementations or a real distributed provider.
