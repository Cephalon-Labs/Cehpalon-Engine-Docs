## Configuration and behavior

Select `JwtKeySource.RotatingKeyRing` on an immutable authentication profile and register `AddCehpalonJwtBearerKeyRing(() => ring)` only inside selected composition. The application owns `JwtKeyRing(profile, maximumSnapshotLifetime, timeProvider)` and its trusted publication path. Empty starts deny. Static callbacks/metadata cannot mix with this mode, and a disabled module never calls its factory. No network refresh or public key-management endpoint was added.

`Publish(expectedVersion, signingKeys, decryptionKeys, notBeforeUtc, expiresAtUtc)` validates/copies a complete candidate before atomically replacing both roles. `Version` is monotonic with checked overflow; stale/concurrent expected versions reject. Publish old+new for overlap, then new-only for retirement. Signing and decryption retirement can differ within one coherent publication. `Withdraw(expectedVersion)` clears future authentication; disposal closes the ring permanently. A failed candidate leaves a still-valid current publication unchanged, and never resurrects expired/withdrawn keys. Trusted UTC plus monotonic elapsed bounds remaining lifetime; default maximum is five minutes and configurable up to one hour. Expiry, observed backward clock movement or clock faults latch that publication invalid until an explicit new publication.

Every validation captures one version for both signing and decryption, uses request-owned key copies and a fresh standard non-caching crypto factory, then checks that version/validity at successful token-handler completion. This prevents mixing nested JWE key generations or returning success after an intervening withdrawal at that gate. Signature-validator overrides that bypass pinned resolvers fail closed. Exact existing signed algorithms and delivered JWE pairs remain; no cipher/package/SDK expansion. Original static/metadata behavior is retained.

Token-handler completion precedes optional asynchronous `OnTokenValidated` callbacks and host ticket caching. Already completed/cached authentication and already admitted business work may finish after withdrawal. There is no transaction with response delivery, retroactive business rollback or distributed session revocation. Fresh tenant selection, membership/resource/RBAC/ABAC, authorized read sets and required operation audit still apply after authentication. Key updates are trusted local management, outside operation audit/history; a durable key-change audit/provider integration remains separate. No raw keys or tokens are recorded.

## Review findings and limits

Returned standard security-token/validation-parameter objects expose mutable references. Request-local copies keep these separate from the active publication. A read-only reviewer reproduced a standard RSA provider-cache hazard with memory-only PowerShell7.6.9 probes using IdentityModel8.19.2 net10.0 assemblies (the host runtime was not separately queried): public JWK conversion exposes shallow RSA parameter arrays; an occupied cached adapter followed by parameter mutation and pool growth can reuse a provider indexed by its original key identity. The diagnostic used reflection to hold an adapter and is a trusted-host object-lifecycle finding, not proof of a remote exploit. Ring validation now assigns a new `CacheSignatureProviders=false` factory to both key roles and local validation parameters. Full pinned-SDK regressions mutate returned converted RSA parameters, check isolated factory identities and run bounded parallel correct/wrong-signer validations. Static profiles were not assigned this extra per-validation work.

The HMAC byte-mutation hypothesis was rejected: `SymmetricSecurityKey.Key` returns a copy in the pinned library. Its regression checks getter-copy isolation and does not claim poisoning of the underlying HMAC key. Separate regressions cover retired-key signature override hooks and partial positive monotonic clock rollback. The reviewer performed source review and small diagnostic probes, not the full SDK suites; root runs final suites separately. Copy/cache-isolation overhead is unmeasured; no speedup, general C# sandbox or exhaustive security certification is claimed.

Primary implementation references: [pinned JWK conversion](https://github.com/AzureAD/azure-activedirectory-identitymodel-extensions-for-dotnet/blob/8.19.2/src/Microsoft.IdentityModel.Tokens/JsonWebKeyConverter.cs), [RSA parameter ownership](https://github.com/AzureAD/azure-activedirectory-identitymodel-extensions-for-dotnet/blob/8.19.2/src/Microsoft.IdentityModel.Tokens/RsaSecurityKey.cs), [signature provider](https://github.com/AzureAD/azure-activedirectory-identitymodel-extensions-for-dotnet/blob/8.19.2/src/Microsoft.IdentityModel.Tokens/AsymmetricSignatureProvider.cs), [provider cache](https://github.com/AzureAD/azure-activedirectory-identitymodel-extensions-for-dotnet/blob/8.19.2/src/Microsoft.IdentityModel.Tokens/CryptoProviderFactory.cs).
